Positron and project structure

Positron is the successor to RStudio, built by the same company (Posit): same R underneath, a more modern editor around it (VS Code based, multi-language, a data explorer, and extensions). Coming from RStudio, see the migration guide.

A project is just a folder you open as a whole (File → Open Folder). Every path in your code is then relative to that folder, so the code runs unchanged on every machine:

adv-r/
├── data/          raw and cleaned data, shared by all modules
├── c01/ … c04/    one folder per module
├── _include/      shared helpers and templates
└── README.md

Rules of thumb: never setwd(), never absolute paths (C:/Users/...), raw data is read-only, and everything that changes data happens in code.

Package management with pacman

Pipes

The base R pipe |> passes the left-hand side as the first argument of the next call. The placeholder _ puts it somewhere else instead, but only into a named argument.

karlsruhe_raw |> nrow()
[1] 48183
karlsruhe_raw |> lm(TXK ~ TNK, data = _)

Call:
lm(formula = TXK ~ TNK, data = karlsruhe_raw)

Coefficients:
(Intercept)          TNK  
      7.749        1.144

Two pipes from the magrittr package are still worth knowing. %$% exposes the columns of a tibble to functions that have no data argument:

karlsruhe_raw %$% cor(TXK, TNK)
[1] 0.8790136

%<>% pipes an object and assigns the result back to it, so the following two lines do the same thing:

rheinstetten_raw <- rheinstetten_raw |> filter(!is.na(TMK))
rheinstetten_raw %<>% filter(!is.na(TMK))

dplyr verbs and SQL

If you know SQL, most dplyr verbs have a direct counterpart. dplyr was designed along the same lines, which is also why DuckDB (below) can translate dplyr code into SQL.

SQL dplyr
SELECT a, b select(a, b)
SELECT a AS new rename(new = a), or select(new = a)
SELECT a * 2 AS b mutate(b = a * 2)
SELECT DISTINCT a distinct(a)
WHERE a > 0 filter(a > 0)
ORDER BY a DESC arrange(desc(a))
GROUP BY g group_by(g)
AVG(a), COUNT(*) summarize(mean(a), n())
HAVING n > 10 filter() after summarize()
LIMIT 10 slice_head(n = 10)
LEFT JOIN ... ON ... left_join(by = ...)
UNION ALL bind_rows()

across(): one function, many columns

The missing-value check above already used across(): it applies the same function to several columns at once. The columns are picked as in select(), e.g. all numeric ones with where():

karlsruhe |>
  summarize(across(where(is.numeric), \(x) mean(x, na.rm = TRUE)))
# A tibble: 1 × 6
  temp_mean temp_max temp_min precip sunshine  snow
      <dbl>    <dbl>    <dbl>  <dbl>    <dbl> <dbl>
1      10.2     14.7     6.06   2.18     4.82 0.454

rowwise()

Most functions are vectorised: given a whole column, they return a whole column. A function built on if is not: it only takes a single value per call, so inside a plain mutate() it fails.

classify_anomaly <- function(anomaly) {
  if (anomaly > 0)
    "warmer" else
    "colder"
}

classify_anomaly(0.8)
[1] "warmer"

Used on the whole anomaly column, it fails, on purpose:

yearly |>
  mutate(sign = classify_anomaly(anomaly))
Error in `mutate()`:
ℹ In argument: `sign = classify_anomaly(anomaly)`.
Caused by error in `if (anomaly > 0) ...`:
! the condition has length > 1

system.time() measures how long its argument takes: elapsed is the wall-clock time in seconds.

DuckDB is a database engine that runs inside R, no server needed. The duckplyr package lets you use it with the same dplyr verbs. read_csv_duckdb() doesn’t read the file at all: it only records the steps. collect() at the end hands the whole query to DuckDB, which reads just the columns it needs, in parallel, and returns only the result.

p_load(duckplyr)

read_csv_duckdb(big_file) |>
  filter(year >= 1996) |>
  summarize(hot_days = sum(temp_max >= 30, na.rm = TRUE), .by = station) |>
  arrange(desc(hot_days)) |>
  collect() |>
  system.time()
   user  system elapsed 
 13.569   1.409   1.677

Both versions start from the CSV file every time. If you query the same data repeatedly, it pays to copy it into a DuckDB database file once. dbConnect() opens (or creates) the file, and one SQL statement copies the CSV into a table. That copy takes a while, but only once:

p_load(duckdb, dbplyr)

con <- dbConnect(duckdb(), "data/big/weather_big.duckdb")

dbExecute(
  con,
  "CREATE OR REPLACE TABLE weather AS SELECT * FROM read_csv('data/big/weather_big.csv')"
) |>
  system.time()
   user  system elapsed 
 34.406   2.567   2.666

tbl() (from dbplyr) points to the table, and the same dplyr verbs become a query against it:

tbl(con, "weather") |>
  filter(year >= 1996) |>
  summarize(hot_days = sum(temp_max >= 30, na.rm = TRUE), .by = station) |>
  arrange(desc(hot_days)) |>
  collect() |>
  system.time()
   user  system elapsed 
  2.463   0.046   0.229 
dbDisconnect(con)

The data now sits in DuckDB’s own column format, so every later query skips parsing the CSV.

Try it: has the warming sped up?

Your task: for each season, compute the warming trend in °C per decade twice, once for the years 1950–2025 and once for 1990–2025. Label each trend as “fast” (more than 0.3 °C per decade), “slow” (above 0) or “none”.

Hint: write a function for one season and start year, then call it once per combination.

season_trend <- function(season_name, start_year) {
  weather |>
    mutate(year = year(date)) |>
    filter(season == season_name, year >= start_year, year <= 2025) |>
    group_by(year) |>
    summarize(temp_mean = mean(temp_mean, na.rm = TRUE)) |>
    lm(temp_mean ~ year, data = _) |>
    tidy() |>
    filter(term == "year") |>
    mutate(per_decade = estimate * 10) |>
    pull(per_decade)
}

expand_grid(
  season = season_names,
  start_year = c(1950, 1990)
) |>
  rowwise() |>
  mutate(per_decade = season_trend(season, start_year)) |>
  ungroup() |>
  mutate(
    trend = case_when(
      per_decade > 0.3 ~ "fast",
      per_decade > 0 ~ "slow",
      .default = "none"
    )
  )
